- [ ] **Accented text never places the excerpt window, so long French files lose the matching lines** `P1`
  - **Context:** `excerptFrom` (`src/core/context/retrieve.ts`) finds the first hit with `line.toLowerCase().includes(term)`, but `extractTerms` folds accents through `foldText` (`src/core/context/terms.ts:89`), so the term `securise` never matches `"Paiement sécurisé"`. Reproduced on a copy of the function: a 6,000-line `fr.json` with the only hit in the middle returns lines 1–471 without `sécurisé`, so the draft cites the head of a locale file that never shows the string it talks about. `src/integrations/jira/client.ts:160` already compares with `foldText`.
  - **Fix:** compare `foldText(line)` in `excerptFrom`. Test in `tests/unit/evidence.test.ts` with `source({...})`: a long file whose only hit is "Paiement sécurisé" between two fillers over 8,000 characters; `evidenceFromPaths(["fr.json"], extractTerms("paiement sécurisé"), …)` must contain the line with `lines.start` within 5 lines of it. Add an ASCII control case so window placement is otherwise unchanged.

## P2 · Production-grade: security, limits, deploy, reliability

- [ ] **Open redirect after sign-in through a tab or newline in `next`** `P2`
  - **Context:** `safePath` (`src/lib/safe-path.ts:3`) only rejects a second character of `/` or `\`. `/sign-in?next=/%09/evil.com` arrives as `"/\t/evil.com"` (`src/app/(auth)/sign-in/page.tsx:8`, same in `sign-up/page.tsx:8`), passes, and `AuthForm` calls `router.push` with it after sign-in (`src/components/auth/auth-form.tsx:19,30`). The URL parser drops tabs and newlines, so it resolves to `https://evil.com/` (confirmed with node; `\n` and `\r\` too), and Next does a full-page navigation (`node_modules/next/dist/client/components/sequential-router-queue.js:85,94`). A phishing link to the real sign-in page sends the victim, right after entering their password, to a fake "session expired" page. The OAuth `returnTo` is safe (`src/features/integrations/notices.ts:16-19`).
  - **Fix:** in `safePath`, parse with `new URL(value, "http://n")`, return the fallback unless `url.origin === "http://n"`, and return `pathname + search + hash`. Unit tests for `"/\t/evil.com"`, `"/\n/evil.com"`, `"/\\evil.com"` and `"//evil.com"`.

- [ ] **Jira bearer tokens are logged when a Jira request times out or the network fails** `P2`
  - **Context:** `jiraRequest` sets `authorization: Bearer <token>` (`src/integrations/jira/client.ts:84`) and wraps only `HTTPError`; other ky errors are rethrown as-is (`:100`). ky 2.2's `TimeoutError` and `NetworkError` keep the `Request` on `.request` (`node_modules/ky/distribution/errors/TimeoutError.js:7-10`), so `console.error` prints `authorization: 'Bearer …'` (confirmed with node). These reach `src/core/context/gather.ts:27`, `src/features/analysis/run.ts:57`, `src/features/analysis/publish.ts:45` and `src/features/integrations/resources.ts:21`: anyone reading host logs gets a Jira token with site-wide read/write for about an hour. `run.ts:57` also logs the AI SDK's `APICallError`, whose `requestBodyValues` holds the full prompt with source excerpts.
  - **Fix:** in `jiraRequest`, catch non-HTTP `isKyError(error)` and throw a plain `Error` naming the type, method and path, without `request` or `cause`. Log `error.name` and `error.message` at the four call sites instead of the raw object. Unit test: a timed-out request's error has no `request` and its inspected output doesn't contain `Bearer`.

- [ ] **Approving from a stale tab publishes an older draft with the new run's sources** `P2`

Evidence ids are positional (`e1…eN`) and `parseApprovedDraft` rebuilds evidence from the current stored result. Scenario: tab A shows run 1; a chat message in tab B produces run 2 with different files; Approve in tab A sends run 1's text with run 2's `e1` attached as its source, passes `validateEvidenceReferences` when the claim has no quoted tokens, creates the Jira issue and overwrites `editedResult` on the run-2 row.

Integration test in `tests/integration/actions.test.ts`: publish with `"run-0"` → error, no tracker call.

- [ ] **Jira action items and decisions run together in audited tickets** `P2`
  - **Context:** in `adfToText` (`src/integrations/jira/adf.ts:93-96`) only `paragraph`, `heading`, `blockquote`, `panel` and card nodes end with a newline; `taskItem` and `decisionItem` hold inline text directly, so items are joined with nothing between them. Reproduced on a copy: a `taskList` ("User can log in", "Errors are shown") and a `decisionList` ("Use OAuth", "Drop SAML") give `"User can log inErrors are shownUse OAuthDrop SAML"`. Teams often write acceptance criteria as action items; the audit model reads merged criteria and `extractTerms` builds terms like `inerrors` (`src/core/analysis/analyze.ts:54`).
  - **Fix:** render `taskItem` as `- [ ] text` / `- [x] text` (from `attrs.state`) and `decisionItem` as `- text`, each ending with `\n`. Add `taskList`/`decisionList` cases to `tests/unit/jira-adf.test.ts`.

- [ ] **Auditing a missing or hidden Jira issue says "the analysis failed, try again"** `P2`
  - **Context:** `parseJiraIssueKey` only checks the format; `tracker.getIssue` (`src/core/analysis/analyze.ts:52`, `src/integrations/jira/client.ts:174-177`) on a typo, deleted or unbrowsable issue throws a 404 `JiraApiError` through `call()`, never a `TrackerRejectedError`, so `recordOutcome` (`src/features/analysis/run.ts:55-62`) shows "The analysis failed. Try again…", which can't help. Publishing has the same gap: `createIssue`'s `issueTypeName()` GET (`client.ts:196-201`) and `applyAuditToTracker`'s `getIssue` (`src/features/ticket-audit/actions.ts:70`) throw unmapped 404s inside `publishApproved` (`src/features/analysis/publish.ts:37-49`), showing "The issue tracker did not confirm the change…" and holding the claim for 2 minutes although nothing was written.
  - **Fix:** map 403/404 on reads to a known error in `JiraClient.call` (or a `TrackerNotFoundError` that `toActionError` maps): "Jira has no issue SHOP-99999, or the connected account cannot see it." Throw `TrackerRejectedError` for "no usable issue type". Add `jira-client` tests for `getIssue` 404 and for a `createIssue` whose project GET returns 404.

- [ ] **Failed analyses record no token usage** `P2`
  - **Context:** usage is saved only on success (`src/features/analysis/run.ts:45-54`). Tokens are lost when the evidence agent runs up to 8 steps then times out or throws (`src/integrations/ai/evidence-agent.ts:52-108`), when drafting fails after the agent succeeded, and when `AiGenerator.run` gets two `NoObjectGeneratedError`s (`discarded` is set in `onFailedAttempt` but pRetry rethrows; `src/integrations/ai/generator.ts:47-66`). The planned usage caps count from the `analysis` table, so repeatedly failing runs are free and cost metrics under-report.
  - **Fix:** pass a usage accumulator (or `onUsage` callback) from `recordOutcome` to the selector and generator, add to it after each model call (including discarded and aborted ones where the SDK reports usage), and write the total on success and failure. Unit test: generator fails twice, the row still gets tokens.

- [ ] **A long Jira Retry-After can let a write land after its publish claim expired** `P2`
  - **Context:** `jiraRequest` retries 429s twice for `post`/`put` (`src/integrations/jira/client.ts:91-96`); ky's `maxRetryAfter` defaults to `Infinity`, there's no `totalTimeout` (`node_modules/ky/distribution/utils/normalize.js:17`) and no abort signal. Two 429s with `Retry-After: 90` land `POST /issue` after 3+ minutes, past `PUBLISH_CLAIM_MS` (2 minutes, `src/core/analysis/stale.ts:11`), so a reload and second approval take a new claim and create a duplicate issue. Reads also wait without limit (`searchRelated` in `gatherContext`), which can push a run past `RUN_BUDGET_MS`.
  - **Fix:** set `retry.maxRetryAfter` (for example 10 s) and a `totalTimeout` well under `PUBLISH_CLAIM_MS` for writes; on a longer Retry-After fail with `TrackerRejectedError` ("Jira is rate limiting; try again in N s"). Test with a 429 carrying a large Retry-After.

- [ ] **Open-question check ignores curly-quoted option values** `P3`
  - **Context:** `DECISIVE_QUOTED` (`src/core/evidence/validate.ts:147`) matches only backticks and straight `"…"`, while `quotedTokens` (line 55) also accepts `“…”`. Confirmed: option `Keep “Free shipping” banner` yields no decisive token, so a claim stating "Free shipping" gets no "leave it undecided" warning when the model or a French user writes typographic quotes.
  - **Fix:** add the `“([^”\n]+)”` alternative to `DECISIVE_QUOTED` and read the third capture in `decisiveTokens`. Test in `tests/unit/validate-evidence.test.ts`: `draft("Show the “Free shipping” banner.", ["Keep “Free shipping” banner"])` yields one issue.

- [ ] **Evidence warnings go stale after saved edits are reloaded** `P3`
  - **Context:** `DraftWorkspace` re-checks warnings only while `edited` is true (`src/components/analysis/draft-workspace.tsx:97`), and after a reload `initial` is the autosaved `editedResult` (`src/features/analysis/read.ts:34`), while the page passes the run-time `analysis.evidenceIssues` (`analyses/[analysisId]/page.tsx:165`) that `saveDraftEdits` never updates. A fixed claim's warning reappears after reload, pointing at text that no longer exists; an edit that breaks a citation shows no warning. Publishing still re-validates.
  - **Fix:** `const shownIssues = evidence ? draftIssues(draft, evidence) : issues;` (same result for an unedited draft). Component test rendering an `initial` draft that differs from the run's issues.

- [ ] **Model and agent timeouts show "ask an admin to check the logs"** `P3`
  - **Context:** `recordOutcome` shows `RUN_TIMEOUT_ERROR` only when the 270 s run deadline aborted (`src/features/analysis/run.ts:60`). The evidence agent stops at 90 s (`src/integrations/ai/evidence-agent.ts:20,101`) and each generator call at 120 s (`src/integrations/ai/generator.ts:18,55`) with a `DOMException` named `TimeoutError` that `toActionError` doesn't map, so the user sees `UNEXPECTED_RUN_ERROR`. Without a second generator attempt the run deadline is unreachable (90 + 120 < 270), so the timeout message almost never appears.
  - **Fix:** use `RUN_TIMEOUT_ERROR` when `deadline.aborted` or `error instanceof Error && error.name === "TimeoutError"`. Test in `tests/integration/analysis-run.test.ts` whose `execute` throws `new DOMException("x", "TimeoutError")`.

- [ ] **Search terms beyond the third are silently dropped and read as "no match"** `P3`

- [ ] **An empty, removed or uninstalled GitHub repository fails every run with a generic error** `P3`
  - **Context:** in `GithubSource.connect` (`src/integrations/github/source.ts:18-27`), a deleted installation fails `getInstallationOctokit`, a repository removed from the App's selection makes `repos.get` 404, and an empty repository makes `getBranch` 404.   - **Fix:** catch 404/403 in `connect` and throw `ConnectionMissingError` (or `ReconnectRequiredError` for a missing installation): "The repository owner/name is no longer accessible to the ContextLayer GitHub App, or it is empty." A `github-source` test per case.

- [ ] **The evidence agent's `<request>` block doesn't defuse tags in the audited ticket** `P3`
  - **Context:** in audits the agent's query is the raw Jira summary and description (`src/core/analysis/analyze.ts:54`) inside `<request>…</request>` (`src/integrations/ai/evidence-agent.ts:55`), while the draft prompt escapes the same text with `asText` (`src/integrations/ai/prompt.ts:8-9`). - [ ] **GitHub API calls have no timeout and wait out rate limits inside a run** `P3`
  - **Context:** the run deadline reaches only model calls (`src/features/analysis/run.ts:43`, `src/features/analysis/context.ts:15-18`). The Octokit `App` has no request timeout or signal (`src/integrations/github/app.ts:20-24`), so `GithubSource.connect`, `readFile` and `searchContent` (`src/integrations/github/source.ts:18-26,77-112`) can hang, and octokit's defaults retry after `retryAfter` on primary and secondary rate limits (`octokit@5.0.5/dist-src/octokit.js:22-39`), so an over-limit code search waits (possibly until the hourly reset) instead of failing into `failedTerms`, holding the server action up to `maxDuration` (300 s) with the row `running`.   - **Fix:** build the App with `Octokit.defaults({ request: { fetch } })` whose fetch adds `AbortSignal.any([AbortSignal.timeout(30_000), runDeadline])`, thread the run deadline through `openSource`, and have `throttle.onRateLimit`/`onSecondaryRateLimit` return `false` for run-time clients.
